2026-11-01 — MAP grows two layers: GRID and STORM (v1.5.4)

The ask started as "add GRID and RAD, four buttons under the map". Recon killed
RAD before any code was written, and that was the right call: EPA RadNet has no
national feed. The only machine-readable source is one CSV per station
(/cdx-radnet-rest/api/rest/csv/<year>/fixed/<ST>/<CITY>), 132 stations, 0.3-0.7 MB
each for the whole year to date, and the server ignores Range headers, so the
cheapest possible sweep is ~90 MB and a day of staleness. Recommending that
against a federal server for a 320-pixel map was not defensible, so the layer
became STORM and the user agreed.

STORM was nearly as tricky for a different reason. NWS /alerts/active returns
~1 MB of CAP documents, and most of them have no geometry at all — 255 of 273 on
the day it was measured. Warnings are issued by zone, so the polygon path only
covers a minority. The fix is the SAME geocode: a 6-digit county code that maps
straight into the census centroid table built for GRID. Note the digit count —
the centroid table is keyed by 5-digit GEOID, so SAME has to lose its leading
state digit (`slice(-5)`); getting that wrong silently drops every zone alert.

GRID itself was easy by comparison: ODIN already had the county rows the
OUTAGES screen uses, and grouping by FIPS in ODSQL is one query. ODIN carries no
coordinates and has no centroid() function, hence the bundled Census gazetteer.
The other surprise was scale — a normal day is ~10k customers across ~150
counties with a median of 5, so any fixed per-county floor below a thousand just
paints noise. The threshold is a query parameter (`?min=`), default 1000.

Layout: the "bar under the map" did not fit. The content column is 194 px, the
aspect-matched map is 170, and the bar needs 14 — with MAP_Y0 at CONTENT_Y+15
there were 10 px left over. Moving the map to +10 makes it add up exactly and
touches nothing else, which mattered because the basemap is generated data with
a fixed aspect ratio. Regenerating us_map_data.h was the alternative; it was not
needed.

Colour: storm was magenta first and the user asked for red plus a triangle. Both
were right. A ring on that map already means earthquake, so the warning layer
needed a shape of its own; red triangles read as hazard signs at 8 px.

Housekeeping that will bite next time:
- The capture build reserves a 76.8 KB sprite; always rebuild the plain release
  afterwards, because merge_bin.py overwrites the committed .bin on every build.
- Gallery images are redacted in place. The MAP shot was fixed by pasting the
  already-redacted city strip from NEWS.png rather than retyping a fake name, so
  the font and position match exactly. Keep doing that.
- GitHub caches README images per URL: MAP.png is now linked as MAP.png?v=2.
- Releases are manual (see RELEASING.md): build both envs, entry in todo.txt,
  commit code + todo + both bins, annotated tag, push branch and tag, then
  `gh release create` with both images attached.

Open threads: the 1,000-customer floor has only been seen on a quiet day — the
first busy day is the real test of whether 80 markers is the right cap. /storms
dedupes by 25 km, which is a guess that has not yet been challenged by a real
outbreak.

2026-11-17 — /cme moves off CCMC, and what the edge can reach

The wall started showing CME DOWN, and the CYD had been quietly reading
0/"NONE" for the same reason. The Worker tail said it in two lines: both DONKI
fetches aborted at the 8 s timeout, and the fallback host had been dead for
months. ccmc.gsfc.nasa.gov answers in under a second from home but hangs from
Cloudflare's egress, on HTTP and HTTPS alike — a blackhole, not a slow server,
which is why the abort fired instead of a status. A throwaway preview worker
settled it: api.nasa.gov/DONKI/CME returned the same 39 KB payload in 426 ms,
kauai refused the connection, CCMC timed out.

The fix is api.nasa.gov as the only source. The catch is that it wants a key,
and DEMO_KEY is the only public one — 10 requests/hour per egress IP. /solar
used to call DONKI itself on a 5-minute loop, so left alone it would have eaten
the whole budget before /cme got a turn. Both now go through one cached fetch:
1 h fresh, 24 h stale, and a 7-day last-good copy in KV (cme:last:v1), which is
what a cold colo serves when the upstream refuses.

The second trap was an interval coincidence: the wall probes every 60 minutes
and the fresh cache lived exactly 60 minutes, so the hourly probe kept landing
on a cold miss. A 429 there was a 500, and SENTINEL LINK stayed DOWN for the
whole hour. That is why the KV copy exists, and why a KV hit refills the fresh
slot for only 2 minutes — retry soon, but never dark.

Verified from the edge: /cme 200 in ~0.1-0.9 s, 12/12 sequential, and a preview
with an invalid key still returned 200 from KV in 312 ms. The CYD needs no
firmware change: it reads cme/cmeTime from /solar and that shape did not move,
so it picks the fix up on its next 15-minute refresh.

Open threads: DEMO_KEY is shared with other Cloudflare tenants, so the KV copy
is the real availability floor; if it ever expires during a long NASA outage
the route goes back to 500. Revisit if NASA offers a keyless DONKI host again.

2026-11-18 — The Oregon quake the map could not see

MaydaySentinel showed M4.2 off the coast of Oregon in the QUAKES panel and
nothing on the MAP. The panel reads the global /quakes list; the map reads
/quakes?us=1, so the first instinct was a client bug. It was not. The CONUS feed
rejected that event twice, and both gates were in the Worker.

The first is the upstream query: us=1 asked USGS for minlongitude=-125, and the
event is at -128.04, so it was never fetched. The second only bites if the first
is widened: isConusPlace matches ", Oregon" / ", OR" in the place string, and
"off the coast of Oregon" has neither. Offshore events have no comma-state by
construction, which is exactly the shape the border-sliver filter was built to
drop.

The fix widens the bbox to lat 22..52, lon -130..-64 (limit 100 -> 200) and adds
isConusOffshore: a phrase test ("off the coast of" / "offshore") accepted only
inside the widened box, with an explicit reject list for foreign coasts —
Mexico, Canada, Baja, Alaska, Hawaii, Cuba, Bahamas, Bermuda, Puerto Rico. The
reject list is the trap worth remembering: "off the coast of Baja California"
reads like a US phrase and tests true on the regex, so the coordinate box alone
does not separate it. Land events still go through isConusPlace untouched, so
widening the bbox drags in Canadian and Mexican land events that the existing
filter already handles; no second land filter was needed.

One more consequence: the query is cached by URL, so the key moved
quakes-us-v2 -> quakes-us-v3 or the old five-minute payload survives the deploy.

Verified from the edge: /quakes?us=1 returns five items, the M4.2 first, plus a
M3.5 and M4.5 also off Oregon on 11/12; CORS is still `*`; the M4.2-adjacent
"35 km ENE of Miguel Ahumada, Mexico" in the widened box is still dropped.
MaydaySentinel got only a label change ("CONUS + US offshore").

Open threads: the offshore phrase list is a guess. "in the Gulf of Mexico" and
"Gulf of Alaska" do not match it — the latter is rightly foreign, the former is
arguably US water, and neither has been seen in the feed yet. Revisit if a US
Gulf event ever goes missing. The wall also still clips points outside the SVG
on narrow/tall stages, so an offshore point can be in the feed and not drawn;
at wall sizes it lands in the ocean margin, which is acceptable, not fixed.
